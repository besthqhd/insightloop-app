# InsightLoop · 从用户反馈到可验证机会

> 面向产品经理、用户研究和运营人员的 AI 产品原型：把零散反馈整理成可追溯洞察，由人完成取舍，再生成 PRD、验收标准和上线验证方案。

[在线演示](https://besthqhd.github.io/insightloop-app/) · [产品需求文档](./InsightLoop_PRD.md) · [竞品分析](./InsightLoop_竞品分析.md) · [真实用户测试审计](./reviews-pipeline/REAL_USER_TEST_V1_AUDIT_2026-09-08.md)

## 为什么做

反馈分析的难点不是“让模型总结一段文字”，而是保证结论能够回答四个问题：

1. 结论来自哪些原始反馈？
2. 数字的分母是什么，记录数和人数是否混用？
3. 哪些是模型建议，哪些是人工决策？
4. 上线后用什么指标判断方案有效？

InsightLoop 因此把 AI 定位为**证据整理者和草稿生成器**，而不是自动决策者。

## 90 秒体验路径

1. 打开「洞察看板」，将数据集切换为「真实用户测试 v1 · 23 条 / 8 人」。
2. 对照主题的记录占比、去重参与者覆盖和证据 ID。
3. 展开「AI 输出质量与确认体验」：该宽泛主题覆盖 8/8 位参与者；其中最强单项证据 `ut_08` 覆盖 6/8。
4. 查看 AI 建议优先级，并填写人工采纳、暂缓或驳回理由。
5. 仅对已采纳机会生成并人工修改 PRD、验收标准和埋点草稿。
6. 点击「转入机会工作区」；系统携带证据、人工理由和最终方案，同一机会再次转入只更新、不重复创建。

## 端到端案例

```text
23 条合并意见 / 8 位参与者
        ↓
5-Agent 结构化分析（JSON 契约、校验、重试）
        ↓
5 个主题 + evidence_ids
        ↓
程序计算记录数、参与者数和占比
        ↓
AI 提议机会和优先级
        ↓
人工采纳 / 暂缓 / 驳回并记录理由
        ↓
PRD + 验收标准 + 埋点草稿
        ↓
转入机会工作区 → 上线验证
```

本轮真实测试得到的可复核结果：

| 主题 | 合并意见记录 | 去重参与者 | 记录占比 | 参与者覆盖 |
|---|---:|---:|---:|---:|
| AI 拆解与细化 | 7 / 23 | 7 / 8 | 30.43% | 87.5% |
| AI 输出质量与确认体验 | 5 / 23 | 8 / 8 | 21.74% | 100% |
| 待办、习惯与总览 | 3 / 23 | 2 / 8 | 13.04% | 25% |
| 日期、日历与设置 | 7 / 23 | 2 / 8 | 30.43% | 25% |
| 导航与界面一致性 | 1 / 23 | 1 / 8 | 4.35% | 12.5% |

这里的 `8/8` 是宽泛主题下多个子意见的参与者并集，不表示 8 位参与者提出了同一个具体问题。单项最强证据是“AI 步骤需要更贴合个人情境”，覆盖 6/8 位参与者。

## 我做出的 AI 产品决策

- **让模型做语义任务，让程序做算术**：模型负责归类和引用 `evidence_ids`；记录数、去重人数和占比由确定性代码计算。
- **把建议和决策分开**：机会优先级明确标为 AI 草稿，只有人工采纳后才能进入方案生成。
- **保留否决权和理由**：暂缓或驳回会禁用后续生成；人工理由也会一起保存。
- **限制无依据扩张**：技术方案统一标记“待代码与技术负责人核实”，不把模型猜测写成事实。
- **让失败可见**：结构化输出经过 JSON 契约校验，并保留失败、重试、版本对比和 Agent 追溯信息。

## 数据与证据边界

项目包含两个用途不同的数据集，不能混为一谈：

| 数据集 | 样本 | 用途 | 不能声称 |
|---|---:|---|---|
| 公开竞品评论 | 143 条，来自 ChatGPT、Kimi、豆包、腾讯元宝、DeepSeek | Evals 与反馈分析链路测试 | 不是 InsightLoop 用户、客户或商业验证 |
| 真实用户测试 v1 | 23 条合并意见，8 位参与者 | 端到端产品决策案例 | 不是 23 位用户，也不是逐字访谈原文 |

不能由现有证据推出用户规模、商业客户、收入、留存提升、转化提升或方案上线效果。数据来源、清洗与限制见 [数据说明](./reviews-pipeline/DATA_README.md)。

## Evals：如何度量 AI 输出

评估看板使用三项代理指标：

- **格式稳定率**：输出能够解析，并通过对应 JSON Schema 必填字段与类型校验的用例数 / 总用例数。
- **至少一项字段命中率**：在已有人工预期标签的用例中，模型至少命中一项受评字段的用例数 / 有标签用例数。它不是完整“任务理解率”。
- **可行动代理通过率**：输出满足预设完整性规则、能够进入下一步人工处理的用例数 / 总用例数。它不是人工“有帮助率”或用户满意度。

仓库当前可展示的单次审计快照，是人工标签修订 v2 的 63 条子集：GLM-4-Flash 为 `100% / 83% / 94%`，Mock 关键词基线为 `100% / 29% / 23%`。这是一次运行和代理指标，不应外推为模型总体能力；详见 [评测证据图](./evals-evidence.svg)。

早期 143 条全量运行曾使用“格式稳定率 / 任务理解率 / 有帮助率”的旧名称，记录过真实模型 `100% / 53% / 99%`、Mock 任务理解率 `66%`。由于后续人工标签和指标定义已调整，这两组结果不能直接做前后提升归因。逐例产物及运行方法见 [Evals 运行说明](./reviews-pipeline/runs/README.md)。

## 系统能力

- 反馈解析、搜索、筛选、CSV / JSON 导入
- 问题分类、情绪识别、多意图拆分和低置信度补采
- 主题聚类、证据引用、记录数与参与者覆盖分离
- 用户研究、数据分析、产品策略、技术评估、协调 5-Agent 链路
- 固定 JSON 契约、脏 JSON 修复、超时与失败重试
- 人工采纳、编辑、版本对比和本地持久化
- PRD、验收标准、埋点与任务拆解草稿
- Mock 与真实模型逐例对比的 Evals 看板
- Cloudflare Worker 密钥托管；API Key 不进入仓库

## 本地运行

项目使用 ES module，请通过静态服务器打开：

```powershell
python -m http.server 8080
```

访问 `http://localhost:8080`。默认使用 Mock，不调用外部模型。

真实模型支持 OpenAI 兼容接口。推荐将 Key 存为 Cloudflare Worker Secret，在 AI 设置中只填写模型名和代理地址。完整配置见 [PRD](./InsightLoop_PRD.md)；可复现命令和无密钥运行产物见 [运行说明](./reviews-pipeline/runs/README.md)。

## 当前状态

这是用于 AI 产品经理求职展示的交互原型，不是已经商业化的 SaaS。已完成单机端到端闭环和可复核运行产物；尚未实现多用户权限、服务端项目数据持久化、正式实验平台和经过上线验证的业务效果。
