# real-user-test-v1 真实模型链路审计（2026-09-08）

- 输入：8 位测试参与者的 23 条按主题合并意见。
- 数据性质：真实用户研究记录的合并转述，不是逐字访谈原文。
- 模型：GLM-4-Flash，经 `insightloop-proxy` 调用。
- 链路：用户研究 → 数据分析 → 产品策略 → 技术评估 → 协调，5 个 Agent 串行。

- 此前两次超时失败亦保留；不从结果集中删除失败运行。

## 原始链路结果

5 个 Agent 均返回通过 JSON 契约校验的 `success`。用户研究 Agent 输出 5 个主题：

| 系统主题 | 系统 count | evidence_ids 数 | 按输入记录应为 |
|---|---:|---:|---:|

| 待办、习惯与总览问题 | 3 | 3 | 3 |
| 日期、日历与设置问题 | 5 | 7 | 7 |
| 导航与界面一致性 | 1 | 1 | 1 |

系统最终建议优先处理“AI 输出质量与确认体验”，priority=9；其次为待办/习惯/总览，priority=8；日期/日历/设置，priority=7。

## 人工审计结论

### 通过项

- 23 个输入 ID 全部进入链路，没有丢失输入记录。
- 5 个 Agent 均成功通过结构化契约。
- 主题基本覆盖了输入中的五个主题域。
- evidence_ids 保留了 `ut_01`–`ut_23` 的可追溯引用。
- 没有编造商业客户、收入、正式用户规模或确定性效果提升。

### Bad cases

1. **主题计数与证据不一致**：AI 拆解主题给出 `count=6`，但列出 7 个证据 ID；日期主题给出 `count=5`，但列出 7 个证据 ID。
2. **占比分母错误**：数据分析 Agent 输出 40%、33.33%、20%、33.33%、6.67%，合计 133.33%；与 23 条输入记录不符。按互斥输入主题记录数，正确占比分别应为 30.43%、21.74%、13.04%、30.43%、4.35%。
3. **记录数与参与者数未区分**：链路没有输出参与者覆盖率，也没有利用 records 中的 `participants` 去重。23 条是合并意见，不是 23 位用户。
4. **最高频判断错误**：协调 Agent 声称“AI 输出质量与确认体验问题反馈最多”，但自身结果中该主题 count=5，低于 AI 拆解主题 count=6；按证据 ID 实际为 5 对 7。
5. **遗漏最高记录主题**：产品策略没有为“AI 拆解与细化问题”生成机会，尽管该主题拥有最多记录证据。
6. **已知强证据被稀释**：输入明确给出“个性化不足 6/8”，系统没有把这个参与者级证据提炼为核心判断。
7. **技术建议缺少依据**：提出“引入预训练模型”“优化数据库结构”“升级后端框架”“接入第三方日历服务”，但输入没有架构证据支持这些结论，应标为待技术核实，而不是直接作为前置条件。
8. **严重度解释矛盾**：数据分析总结称导航问题“严重性较高，被标记为 P3”，但现有口径中 P3 是低于 P2 的优化建议。
9. **汇总数学错误**：声称四类问题“占总反馈的80%”，无法由其自身输出的 count 或 share_pct 推导。

## 本次测试结论

InsightLoop 已证明真实模型链路能够完成结构化聚类和证据引用，但**尚不能可靠地自动完成计数、参与者去重、占比计算、优先级排序或技术决策**。本次输出必须保持“AI 草稿、人工审核后采纳”状态。

下一轮应优先修复确定性计算，而不是继续用 Prompt 要模型做算术：

1. 用户研究 Agent 只负责主题归类和 evidence_ids；`count` 由程序按唯一 evidence ID 计算。
2. 同时计算 `record_count` 与去重后的 `participant_count`，禁止混用。
3. share_pct 由程序以明确分母计算，并校验互斥主题合计约为 100%。
4. 产品策略输入必须包含经过校验的排序，并要求解释为何跳过最高证据主题。
5. 技术评估的架构性结论统一标记为“待代码/技术负责人核实”。

## 不应声称

- 不应称“AI 输出质量问题占 33.33%”或“反馈最多”。
- 不应称“数据库重构、后端升级或第三方日历服务是必要方案”。
- 不应把单次成功运行当作稳定性结论；本轮另有两次超时失败。
- 不应把 23 条合并意见称为 23 位用户反馈。
